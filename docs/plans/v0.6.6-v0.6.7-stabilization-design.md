## Purpose

nim-proxy has a working pre-1.0 product built through rapid prototyping. The
proxy's core value is already clear: pace requests without upstream
rate-limit violations, balance NVIDIA NIM keys, and keep clients connected
while requests wait. The work now is to make the repository, contracts, and
operator experience look intentional before 1.0.

This is maintenance, not a feature expansion. Prototype vocabulary,
hand-authored UI strings, inconsistent response shapes, incomplete browser
coverage, and guessed observability semantics are design debt that should not
become permanent compatibility promises.

The existing integration branch contains substantial useful work, but its
process and several claims were unreliable. The branch will be audited and
repaired through small, proof-driven work items rather than discarded or
merged wholesale.

## Decisions at a glance

1. Repair the current integration branch. Keep `main` untouched until the
   integration PR is accepted.
2. Treat pre-1.0 machine-contract changes as deliberate maintenance. Document
   breaks; do not preserve accidental interfaces solely because they exist.
3. Stabilize intent and English terminology before producing the production
   locale pack.
4. Ship the contract/presentation foundation in v0.6.6 and production
   localization in a v0.6.7 milestone created after plan approval.
5. Keep the runtime a tiny, rootless, distroless, self-contained Rust binary.
   Source assets may be split for maintainability and embedded at compile time.
6. Use native browser facilities and existing dependencies before adding
   machinery.
7. Replace the experimental history formats with one unambiguously
   discriminated canonical format named `nimproxy-history/v1`. Existing history
   resets at upgrade; no compatibility migration is carried.
8. Keep proxied responses transparent. Preserve only the existing documented
   streaming usage-injection/fallback request exception; observability adds no
   new request mutation and drops invalid optional measurements instead.
9. Make committed checks the first deliverable for behavioral changes.
10. Use `docs/plans/` for decisions and proof contracts, GitHub for live work
    state, and `knowledge/` for durable post-proof understanding.

## Non-negotiable product invariants

The stabilization program must preserve these invariants:

- Pre-setup data-plane access remains closed.
- Post-setup operator surfaces require the documented session or API role.
- Corrupt or future configuration stores refuse to boot.
- The proxy produces zero upstream rate-limit violations.
- Proxied model ids, client names, publisher names, prompts, response content,
  and metric label values remain machine data and are never localized.
- Upstream response bytes are not rewritten to satisfy dashboard assumptions.
  Request mutation remains limited to the existing documented automatic
  `stream_options.include_usage` injection, its untouched retry on rejection,
  and the `strict_passthrough` opt-out.
- New presentation work does not rename DOM ids, `data-*` attributes, CSS
  classes, config keys, metric series, or sort keys accidentally. Deliberate
  machine-contract changes are separately inventoried, tested, and documented.
- The application retains no runtime dependency on a translation service,
  CDN, frontend build system, or external database.

## Vocabulary and presentation model

### Intent before wording

Every visible string is classified by intent before it is renamed or
translated:

- navigation and surface names;
- actions and destructive actions;
- current state and historical state;
- proxy scheduling, capacity, and rate-limit concepts;
- client, model, key, and request observations;
- validation, error, empty, warning, and success messages;
- help text and accessibility descriptions;
- machine data that must pass through unchanged.

The replacement vocabulary uses common proxy, load-balancer, authentication,
and operations language. Prototype metaphors such as lanes are removed from
operator text. Similar concepts receive one term; distinct concepts do not
share a convenient but inaccurate label.

The inventory records the original string, its actual intent, the canonical
English replacement, its surface, whether it contains machine data, and the
proof that renders it.

### Source organization

The browser runtime remains framework-free and build-free. HTML, JavaScript,
CSS, and catalogs are separated into maintainable source files, embedded in the
Rust binary with `include_str!`/`include_bytes!`, and served from explicit
same-origin asset routes. HTML page routes retain their setup/session gates.
Only the minimal setup/login asset subset is public; dashboard, Settings, and
operator-catalog assets pass through the same post-setup session gate as their
HTML surface. Assets are immutable, contain no configuration or secrets, and
are inventoried in the route/trust matrix. This supports a CSP based on
`script-src 'self'` and `style-src 'self'` without inline handlers.

One canonical source catalog remains authoritative. The committed locale
generator derives a public subset containing only `setup.*`, `login.*`, and
explicitly public common ids; validators prove that the subset is an exact
projection and contains no operator-only ids. A public typed locale-bootstrap
endpoint exposes only the installed locale tags and server default. Setup/login
JavaScript combines that response with browser preferences and fetches the
matching public subset. The full/operator catalog remains session-gated.

The source organization should make these boundaries visible:

- shared presentation primitives;
- dashboard behavior;
- Settings behavior;
- setup/login behavior;
- styles;
- locale catalogs.

No component abstraction is introduced merely to imitate a frontend framework.
Native elements such as `<button>`, `<dialog>`, tables, headings, landmarks,
forms, CSS, SVG, and DOM APIs are preferred.

The current Google Fonts and unpkg icon dependencies are removed. The UI uses a
system font stack and locally embedded/static SVG or text primitives already
owned by the project. A committed check rejects runtime `http://` or `https://`
asset dependencies. No font or icon package is added.

### Plain catalogs and contextual sinks

The owner approved superseding the existing "escape catalog text at load"
decision. That approval is not self-executing: the first presentation work item
must update `AGENTS.md`, replace
`knowledge/decisions/message-catalog-and-escaping.md`, inventory every
`innerHTML`, attribute, URL, style, event, script, and SVG sink, and add the
negative sink tests before changing `t()` or a render helper. Until that
atomic work item lands, the current escape-at-load invariant remains binding.

- Catalog files store plain Unicode text.
- `t()` returns plain text, not HTML-escaped text.
- Normal content is assigned with `textContent`.
- Localizable attributes are restricted to an explicit text-bearing allowlist
  and assigned with `setAttribute`.
- Inline emphasis, links, or other structured messages use structured DOM
  construction, not translator-authored HTML.
- Any unavoidable HTML string sink performs exactly one context-appropriate
  escape at that sink.
- Catalog values never enter `style`, URL, event-handler, script, CSS, or raw
  SVG contexts.

Validators and negative self-tests enforce this policy. Rendering checks prove
both literal display and resistance to markup injection.

## Localization architecture

### Catalogs and resolution

There is one complete catalog per locale. All operator-visible strings,
including validation and accessibility text, use catalog ids. API values and
upstream data remain untouched.

Locale selection resolves in this order:

1. explicit authenticated-user preference;
2. compatible browser language;
3. server default;
4. `en-US`.

The resolved locale is applied consistently to messages, sorting, numbers,
dates, times, percentages, and plural categories through native `Intl`
facilities. `en-XA` is generated and test-only.

v0.6.6 adds the dormant contract: an optional BCP 47 locale preference on the
authenticated operator record, a server default in the managed configuration,
the public locale-bootstrap response, and typed read/update fields in the
relevant control-plane API and OpenAPI. The config store remains schema v1:
these are additive `#[serde(default)]` fields, not a new migration framework or
version bump. Existing records therefore read as no explicit preference and
server default `en-US`; the next ordinary save persists the fields.
Authorization follows the existing settings/user role matrix. A requested but
uninstalled locale is rejected with a stable error code. v0.6.7 adds installed
catalogs, not a new persistence or endpoint shape.

### Generation and provenance

English is the authored source. Production catalogs are generated offline
through a committed script using the existing OpenAI-compatible client path and
standard-library file handling.

Generation is not a CI dependency. Catalogs are checked in and CI is
deterministic.

Each entry's lifecycle distinguishes:

- **Source** — canonical English;
- **Machine** — generated from the current source;
- **Reviewed** — human-approved wording;
- **Stale** — source changed after translation or review.

The generator can use an LLM judge during generation, but runtime and CI never
call a model. Existing translations and human review are preserved unless the
English source actually changed.

### Locale validation

The existing locale and i18n validators are extended rather than replaced.
They must reject:

- missing or extra catalog ids;
- invalid or non-canonical locale tags;
- markup or entity-encoded markup;
- placeholders not authorized by the English source;
- missing plural categories required by the locale;
- stale pseudolocale output;
- untagged visible English;
- catalog data routed to a forbidden attribute or sink.

Every rule receives a negative fixture and self-test that has been observed to
fail for that rule specifically.

## API and trust-boundary rationalization

### Boundary inventory

Every route is captured in a contract matrix with:

- consumer;
- public or private classification;
- pre-setup and post-setup availability;
- authentication mechanism and role;
- request type;
- success type;
- stable error codes;
- persistence or upstream side effects;
- UI call sites;
- OpenAPI coverage;
- committed tests.

The inventory covers the data plane, control plane, setup/bootstrap, session
surfaces, metrics, health, static assets, configuration, and generated
OpenAPI.

Two flows receive end-to-end documentation:

1. client → authentication → dispatcher → key selection → rate limit → model
   governor → NIM → response → observations/history → dashboard;
2. operator UI → session/role → control-plane handler → validation →
   configuration store → runtime state.

### Typed contracts

Control-plane success and error responses use Rust types. Errors use a
consistent envelope and stable machine-readable codes. Extractor and
middleware failures return the same documented JSON contract rather than
framework-default text.

OpenAPI is generated from the same handler/types and committed. Its documented
security schemes must match real accepted authentication. Description-only
authentication behavior is not an adequate contract.

The current branch deliberately treats ASCII-sorted JSON member order as part
of its compatibility contract. That guard remains. The existing test is
repaired to assert raw serialized bytes rather than a `serde_json::Value` map
whose sorting can make the assertion vacuous. Meaning, names, types, status
codes, security, examples, and the documented order are tested.

The proxied `/v1` response surface remains byte-transparent except for the
already documented streaming heartbeat/error behavior. Requests retain the
existing documented automatic `stream_options.include_usage` injection,
untouched retry when the upstream rejects it, and `strict_passthrough` opt-out.
Scheduling, authentication, retry, and deadlines retain their documented
transport behavior. Observation work does not create another mutation path.

## Canonical `nimproxy-history/v1`

### Compatibility policy

The experimental rows currently called v1 and v2 in the implementation are not
public compatibility obligations. To avoid confusing the new format with
either one, every canonical record carries both
`"format":"nimproxy-history"` and `"v":1`, plus a bounded `kind`.

Canonical records live at `history-v1.jsonl`. Experimental `history.jsonl`
remains byte-for-byte untouched and is never parsed by the new reader. Release
notes and a bounded startup warning state that dashboard history reset, report
the legacy path/size, and explain when the operator can delete it or retain it
for rollback.

Startup follows an explicit state machine:

1. If `history-v1.jsonl` is absent, write a canonical boot record to a unique
   same-directory temporary file, flush and sync it, publish it without
   overwrite using `std::fs::hard_link`, remove the temporary name, and sync
   the directory before serving. This uses the standard library and gives
   concurrent first creators one winner without a check-then-rename race.
2. A crash before the hard link leaves the canonical path absent. The next boot
   creates a different unique temporary file; stale known-prefix temporary
   files are ignored and reported as cleanup debt, never parsed as history.
3. A crash after the hard link leaves a complete canonical boot record; it may
   also leave the harmless temporary name, which is reported but not parsed or
   automatically deleted.
4. A zero-length or whitespace-only canonical path, or any record that declares
   a format other than `nimproxy-history` or version other than 1, refuses
   startup and remains byte-for-byte untouched. Other undecodable rows and
   unknown v1 kinds—including the first nonblank row—follow the recoverable
   corruption rules below and remain byte-for-byte evidence. Existence is never
   treated as absence.
5. A valid existing canonical file is scanned under the corruption rules
   below, then a fresh boot record is appended and synced before serving so
   every process start establishes a reset boundary.
6. Experimental `history.jsonl`, if present, is never renamed, truncated,
   removed, or parsed. Its presence produces the bounded legacy warning only.

Failure-injection tests cover every transition and prove that both history
files, `config.json`, credentials, and session/authentication state have the
specified byte-preservation behavior.

This is deliberately different from configuration-store handling. History is
disposable analytical state; configuration and authentication remain
fail-closed durable state.

### Record model

Canonical v1 has three record kinds, each carrying the discriminator:

- **boot** — timestamp, boot identity, and capacity boundary;
- **sample** — timestamp, boot identity, capacity, and a full normalized metric
  state;
- **checkpoint** — timestamp, boot identity, and capacity, carrying the
  preceding metric state without repeating it.

The writer compares normalized bounded metric state, never raw Prometheus text
whose line order is unstable. It writes a full sample only when metric state
changes and a small checkpoint otherwise.

Readers expand checkpoints as carry-forward state. Rollups retain:

- five-minute time precision;
- explicit boot/reset boundaries;
- contemporaneous capacity;
- exact counter totals independent of chart point budget;
- current-tail revision protection;
- retention-boundary baselines;
- atomic compaction.

Unknown non-state object fields are ignored for forward-compatible additive
metadata. Observation collection drops invalid optional upstream fields before
they can become persisted metrics. Once written, every metric state entry is
state-bearing; an invalid entry invalidates the full sample rather than being
silently omitted. Corruption handling depends on semantic role:

- An invalid full sample ends the current recoverable segment and is counted in
  bounded diagnostics. Checkpoints are ignored until the next valid full
  sample.
- An orphan or malformed checkpoint is ignored and cannot carry state across a
  gap.
- A malformed boot record invalidates that epoch; rows are ignored until the
  next valid boot and full sample.
- An undecodable JSON line inside a canonical file has unknown semantic role,
  so it invalidates the current epoch. No subsequent row is trusted until a new
  valid boot record followed by a valid full sample establishes both the reset
  boundary and complete state.
- A future declared format/version refuses startup as described above.

Rollup totals are exact over valid contiguous segments. When corruption creates
an excluded segment, the API exposes incomplete-history diagnostics and does
not label the cross-gap result exact. Normal writer output is required to
round-trip without any exclusions.

### Rejected alternatives

- Preserve all experimental history versions: rejected pre-1.0 compatibility
  cost.
- Rename or rotate the experimental file automatically: rejected because a
  distinct canonical filename avoids destructive upgrade and crash-recovery
  states while preserving rollback.
- Skip idle timestamps entirely: rejected because historical time/capacity
  boundaries would become ambiguous.
- Compress repeated full snapshots: rejected because it retains unnecessary
  serialization and complicates inspection/compaction.
- Add SQLite or a TSDB: rejected because the versioned JSONL design is
  sufficient once unchanged state is represented correctly.
- Increase the sampling interval: rejected because it changes operator-visible
  time precision rather than fixing duplication.

## Evidence-driven NIM observations

### Current evidence

The production-like history file proved that full cumulative snapshots were
being rewritten during idle periods. Rambler's tournament artifacts provide
normalized buffered completion evidence across multiple NIM models, including
finish reason, token usage, cached-token details, model/id, content, and
reasoning content.

The bounded sample established:

- both `stop` and `length` finish reasons occur;
- prompt, completion, and total token counts were internally consistent;
- `prompt_tokens_details.cached_tokens` is optional;
- reasoning content can be present while
  `completion_tokens_details.reasoning_tokens` is absent.

Therefore absence is not measured zero. A dashboard must not present a missing
reasoning-token observation as proof that a model performed no reasoning.

### Collection policy

The proxy forwards upstream response bodies unchanged. Requests retain only
the documented usage-injection/fallback exception above. Observation values
follow explicit validity rules:

- token fields must be JSON integers in `0..=u64::MAX`;
- prompt, completion, and total tokens are validated independently;
- `prompt + completion` uses checked addition; overflow makes the relationship
  invalid without invalidating either base field;
- a total smaller than a non-overflowing `prompt + completion` is invalid while
  the valid base fields remain usable;
- cached tokens are usable only with a valid prompt count and must not exceed
  it;
- reasoning tokens are usable only with a valid completion count and must not
  exceed it;
- one invalid child does not erase an unrelated valid sibling;
- a valid zero is measured zero;
- a missing field with no allowed estimator is unavailable;
- a present mistyped, negative, overflowing, or relationship-inconsistent field
  is invalid;
- stream estimates are labeled as estimates and never presented as usage;
- finish reasons and diagnostic reasons map to fixed bounded enums.

Availability is measured with a bounded observation counter keyed only by a
fixed field enum and a fixed result enum (`measured`, `estimated`,
`unavailable`, `invalid`). Dashboard ratios use only observations with the
required measured denominator/numerator and display unavailable separately
from zero. These new series and any API availability fields are inventoried as
deliberate machine-contract changes.

The implementation plan includes a field/outcome matrix for prompt,
completion, total, cached, and reasoning tokens. For every field: absent maps
to unavailable unless the one documented stream estimator applies; valid maps
to measured; an estimate maps to estimated; and any present type, range, or
relationship violation maps to invalid. Negative fixtures assert each cell and
prove one invalid child does not erase unrelated valid siblings.

Malformed optional usage is silent to the client. Diagnostics contain no model
ids, prompts, content, unbounded upstream field names, or raw values.

### Evidence gaps

Rambler normalized its buffered responses and did not retain complete raw HTTP
envelopes or SSE events. Controlled, sanitized fixtures are still required for:

- streamed usage and missing-usage fallback;
- split SSE lines and terminal chunks;
- tool calls and tool-call indexes;
- multiple choices;
- alternate or unknown finish reasons;
- cached and reasoning token details;
- upstream non-JSON and structured error bodies;
- stalled and interrupted streams.

Capture uses a committed, stdlib-first diagnostic script with credentials only
from environment variables. It sends synthetic, non-personal prompts through a
controlled local proxy/NIM path, writes raw output only to a newly created
temporary directory, and produces a separate sanitized candidate fixture.
Sanitization replaces content, ids, and secrets while preserving event
boundaries, field presence, JSON types, numeric relationships, status, and
headers needed by the parser. A human diff review is required before a fixture
is committed; the raw temporary capture is then deleted. Model ids may remain
only when they are necessary provenance and are explicitly reviewed.

The sanitizer has a committed self-test built from a synthetic hostile raw
capture containing authorization headers, API keys, cookies, prompt/content
canaries, ids, multiline SSE events, and misleading near-match fields. The test
must first demonstrate a specific leak when the relevant sanitizer rule is
disabled, then prove all canaries are absent while required event boundaries,
types, statuses, and allowlisted headers remain. Human review is an additional
gate, not the proof.

## Verification architecture

### Per-work-item TDD loop

Every behavioral work item follows:

1. add or extend a committed check;
2. observe it fail for the intended reason;
3. make the minimum implementation change;
4. run the named proof;
5. run adjacent regression checks;
6. run a fresh adversarial reviewer before commit.

A hand-built scratch proof can show that a committed check bites, but it is not
the final deliverable.

### Rust and contract tests

Rust tests cover:

- auth and route-role matrices;
- typed success/error contracts;
- extractor and middleware failures;
- OpenAPI drift;
- history v1 parsing, checkpoint expansion, resets, retention, and compaction;
- exact rollup equivalence between repeated samples and checkpoints;
- response-observation parsers against sanitized real fixtures;
- configuration and intentional breaking migrations.

Pacing, pool, dispatcher, and governor changes additionally require the strict
mock/load test with zero upstream violations.

### Browser tests

The existing Node/Chrome DevTools render harness is repaired and extended
rather than replaced with a new browser framework.

It must:

- boot pages against responses produced from real Rust types/handlers;
- require successful initial fetch and render, not merely absence of an
  uncaught exception;
- visit all analytical tabs and Settings panels;
- drive setup, login, validation, dialogs, destructive actions, and role
  restrictions;
- exercise keyboard and focus behavior;
- hover charts and dynamic content;
- run under `en-US`, `en-XA`, and each production locale when introduced;
- fail on visible untagged English, forbidden markup, double escaping,
  console/page errors, and failed requests.

Layout receives both mechanical overflow probes and human screenshot review at
supported widths. Behavioral success is not treated as proof that text fits.

### Fixture ownership

UI API fixtures are generated from the Rust contract rather than independently
hand-maintained. Update mode rewrites committed fixtures; check mode fails on
drift.

Locale, i18n, formatter, OpenAPI, render, and history validators retain
negative self-tests that assert which rule fired.

## OKF-native agent instructions

Before implementation resumes, rewrite `AGENTS.md` as the stable operating
contract and router for the repository's Open Knowledge Format bundle. It must
not duplicate inventories, proof matrices, incident narratives, exact counts,
or other facts that change with the codebase.

The rewrite is a lossless migration, not a deletion pass. Before removing a
durable proof rule from `AGENTS.md`, reconcile it into
`knowledge/testing/test-strategy.md`. This includes Rust, OpenAPI, JavaScript
syntax, dashboard and setup rendering, locale, i18n, formatter,
pseudolocale, layout, load, and formatting gates. The implementation review
compares the old guide with the new guide and test-strategy page together; a
rule is not displaced until its destination is present and accurate.

The repository memory follows the LLM-wiki operations:

1. **Query** — read the applicable plan, orient through
   `knowledge/index.md`, search `knowledge/` for the concept and its synonyms,
   read the relevant concept pages completely, search `knowledge/log.md` for
   chronology and gotchas, then follow relative links. Use file history when
   the evolution of a claim matters.
2. **Ingest** — promote verified facts, settled decisions, component
   understanding, and repeatable procedures into one durable concept page.
   The log records that the ingest happened; it is not the only home of the
   resulting knowledge.
3. **Lint** — look for contradictions, stale claims, orphan pages, missing
   cross-references, duplicate concepts, and durable facts stranded only in
   chronology.

`knowledge/index.md` remains the agent-maintained semantic catalog and
progressive-disclosure entry point. `knowledge/log.md` remains append-only
chronology with greppable entry prefixes. Neither is reproduced as a
hand-maintained table in `AGENTS.md`, and no generator, database, search
service, or new schema is introduced.

The rewritten guide retains only:

- startup and memory-retrieval order;
- every currently binding product and security invariant;
- stable repository operations for worktrees, integration branches, and PR
  targets;
- Plan → Act → Verify, scope-delta, TDD, and independent-review rules;
- the Ponytail ladder;
- proof routing through `knowledge/testing/test-strategy.md`;
- the Query → Ingest → Lint memory contract;
- authority boundaries among plans, code, knowledge, GitHub, and external
  systems.

The current escape-at-load contract remains explicit and binding in the guide.
Only the separately approved atomic presentation work item may replace it,
after its decision page, sink inventory, negative tests, and agent instructions
land together. The same rule applies to any other non-negotiable: this rewrite
may clarify its scope but cannot silently weaken or retire it.

The first implementation deliverable is a repository-local, Python-stdlib
validator at `scripts/check_agent_guide.py`. Its `--selftest` mode proves the
checker rejects a missing local link and each required structural contract.
The normal mode verifies that local Markdown links resolve and that the guide
contains the stable memory, planning, invariant, proof-routing, and authority
contracts. A failure exits nonzero and names the missing link or contract.
CI and local verification call the same committed command; no inline workflow
copy is maintained.

Repository operations are standing authorization, not a recurring question.
For each independently reviewable work item, create an isolated worktree on a
task branch based on the integration branch named by the active plan. The
work-item PR targets that integration branch. The integration branch remains
isolated from `main`; only its final integration PR targets `main`. Verify the
worktree directory is ignored, preserve unrelated work, and remove the
worktree only after the task branch is safely integrated. Do not hard-code a
release branch name in `AGENTS.md`; resolve it from the active plan.

Code is evidence of current behavior. Knowledge records approved
understanding, intent, constraints, and rationale. A mismatch is investigated
as a defect or stale-memory finding; neither side is silently rewritten to
match the other.

Project fields:

- built-in `Status`;
- `Workstream`: Presentation, API/Boundaries, History/Observability, Testing,
  Localization, Knowledge/Release;
- `Risk`: Low, UI, Contract, Persistence, Security, Data plane;
- `Priority`: P0, P1, P2.

Do not duplicate milestone, issue type, assignee, labels, parent progress, or
linked-PR state in custom fields.

Views:

1. **Current release** — board grouped by Status and filtered to the active
   milestone.
2. **Workstreams** — table grouped by Workstream with parent and sub-issue
   progress.
3. **Blocked and risk** — table filtered to dependencies, P0/P1, or
   Security/Data-plane/Persistence risk.

Dates, estimates, iterations, and roadmap views are omitted until there is a
real scheduling question.

### Source-of-truth split

- This design and subsequent implementation plan own scope, architecture,
  constraints, proof contracts, the complete work-item inventory, and status
  required by repository instructions.
- GitHub mirrors owner-facing status and owns issue discussion, priority,
  relationships, milestone assignment, and linked PRs.
- Knowledge owns durable explanations after proof.

Every status transition updates the plan and GitHub in the same work item. If
Projects authorization or network access is unavailable, the plan is updated
and the GitHub synchronization remains an explicit pending task. The plan is
the conflict authority, so agents can continue safely from a local checkout.

## Recovery and integration strategy

The integration branch remains the recovery vehicle. Work proceeds through
focused branches/PRs into `release/v0.6.6`, never directly into `main`.

Each work item:

- identifies which existing commits/files it retains, replaces, or removes;
- begins with its proof;
- updates affected knowledge;
- receives an adversarial review;
- lands only when its issue acceptance criteria are met.

The final integration PR is reviewed as the cumulative release diff against
`main`, with full CI, strict load proof, browser evidence, breaking-change
notes, and release-contract verification. It is squash-merged only after owner
acceptance.

## Explicit non-goals

- General-purpose API gateway behavior
- Prompt or response logging
- Runtime machine translation
- Translator-authored HTML
- RTL layout in the initial locale pack
- Frontend framework or package/build pipeline
- External database or TSDB
- Preservation of experimental history files
- Arbitrary rewriting of incompatible NIM responses
- Pricing or speculative savings metrics
- Companion CLI
- Work estimates or release dates without an actual scheduling need
